# 评分即解题

**提出者**：fangzhiyu
**日期**：2026年3月27日
**来源**：华为 MTV 比赛中 LLM 进化实践的核心洞察

## 定义

只要你能对一个问题的解进行自动评分，LLM 进化就能替你解题。人的角色从"解题者"变成"评委"。评分比解题简单得多——这个不对称性是 LLM 进化优化的根基。

## 核心不对称

| | 难度 | 所需知识 |
|--|------|---------|
| 设计最优凸分解算法 | 读 20 篇论文，理解计算几何 | 深度专业知识 |
| 判断一个凸分解是不是比另一个快 | 跑一下，比时间 | 零专业知识 |
| 写出高性能排序算法 | 理解分治、缓存、分支预测 | 系统底层知识 |
| 判断一个排序实现的速度 | benchmark | 零专业知识 |

## 实证

华为 MTV 比赛中，fangzhiyu 没有学习计算几何的 Minkowski Sum、Hertel-Mehlhorn 凸分解等算法。他搭建了评测管线（Docker + ARM 官方 Runner），让 ShinkaEvolve 自动进化。结果：

- 进化独立发明了双层空间索引（UniformGrid for polygons + boundary segments）
- 发明了 generation counter 去重、CachedPoly 预计算
- 通过 full rewrite 产出了完全不同的算法架构
- 人工手动尝试相同优化（grid for boundary）反而更慢，进化找到了正确的实现方式

## 范式对比

```
旧范式：人理解问题 → 人设计算法 → 人写代码 → 人调优
新范式：人定义评分 → 人搭框架 → LLM 探索解空间 → 进化筛选最优
```

类比深度学习的范式转移：你不需要手写特征提取，你只需要定义 loss function。

## 适用条件

1. **有明确的自动化评分函数** — 能用程序判断好坏
2. **评分成本可接受** — 每次评分在秒到分钟级
3. **解空间足够大** — LLM 有创造力的空间
4. **LLM 有领域知识** — 知道相关算法和技术（不需要人知道）

## 不适用的场景

- 评分本身需要人类判断（如"这个 UI 好不好看"）
- 评分成本极高（如需要真实用户测试）
- 问题过于简单（人写比进化快）

## 更恐怖的推广

任何有明确评分函数的工程问题都能用这个范式：

- 编译器优化（评分 = benchmark 时间）
- 数据库查询优化（评分 = QPS）
- 芯片布局（评分 = 仿真功耗）
- 药物分子设计（评分 = 对接能量）
