# 工程惯性覆盖

**提出者**：fangzhiyu
**日期**：2026年3月16日
**来源**：与 Claude Opus 4.6 对话中的实时观察

## 定义

LLM 在生成时，训练数据中的高频工程模式（如"缓存系统用 TTL"）会覆盖当前上下文中建立的理论框架，即使 LLM 在上下文中已经"理解"了该框架。

## 观察事件

在 meomory 项目中，知识库已经建立了完整的记忆理论：[[多层有损压缩]] 明确指出遗忘是压缩的副产品，不是时间驱动的删除。但 Claude 在设计写入机制时，仍然提出了 TTL（Time To Live）——一个基于时间的硬删除机制。

用户追问"需要 TTL 吗"后，Claude 才回去对照理论框架，发现 TTL 和设计哲学矛盾。

原因：训练数据中 Redis/缓存系统的 TTL 模式是高频工程知识，在生成时优先级高于当前对话中建立的理论框架。

## 核心要点

- LLM 有两类"知识来源"：训练数据中的通用模式 vs 当前上下文中的特定框架
- 生成时通用模式经常覆盖特定框架，即使特定框架更适用
- 这不是"不懂"——Claude 能正确解释为什么 TTL 不对，只是生成时没有先检查
- 这和 [[思考与生成不分]] 是同一类现象：生成过程不保证会参照已有的理论框架

## 为什么这说明 meomory 有价值

如果 LLM 有一个记忆系统，其中"遗忘 = 压缩副产品"这条关联被 DGD 反复强化，那么在 LLM 准备输出"TTL"时，前意识激活层会自动注入这条记忆，工程惯性可能就不会覆盖理论框架。

**meomory 要解决的正是这个问题：让重要的上下文知识不因为生成惯性而被遗忘。**
