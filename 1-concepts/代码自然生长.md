# 代码自然生长

**提出者**：fangzhiyu
**日期**：2026年3月17日
**来源**：从 Self-evolution-agent-java 到 meomory FunSearch 的实践总结

## 定义

代码不是写出来的，是长出来的。人类的角色从"编写代码"转变为"定义评测函数"，代码通过进化自动生长、自动测试、自动优化。

## 核心公式

```
能进化 = 代码化 + 自动评测

人定义: 什么是"好" (评测函数)
AI 做:  生成变体 → 评测 → 淘汰 → 保留 → 继续生成
```

## 与现有范式的区别

| | 传统编程 | Software 2.0 (Karpathy) | 代码自然生长 |
|--|---------|------------------------|------------|
| 核心 | 人写规则 | 数据训练模型 | 进化生成代码 |
| 人的角色 | 写代码 | 标注数据 | **定义评测函数** |
| 产物 | 确定的程序 | 神经网络权重 | **进化出的程序** |
| 可解释 | 高 | 低 | 中（代码可读但组合不直观） |
| 适应性 | 无（改了才变） | 重训才变 | **持续进化** |

## 已验证的阶段

```
2025.11  ✓ 进化单个函数（排序算法，Java）
2026.03  ✓ 进化单个类（AssociativeMemory，Python）
2026.03  ✓ 进化 prompt（Judge prompt，90.9%）
2026.03  ✓ 多模型协同进化（9b + DeepSeek + GPT-5.4）
```

## 未验证的阶段

```

◯ 进化整个服务/pipeline
◯ 进化进化策略本身（自指涉——PromptBreeder 在 prompt 层做了）
```

## 实践中的约束

**能进化的：**
- 能写成代码的（算法、策略、配置、prompt）
- 能自动评分的（有量化指标、有测试集、有 GT）

**不能进化的（目前）：**
- 不能代码化的（审美、情感、价值判断）
- 不能自动评分的（需要人类判断质量的）
- 搜索空间过大的（整个操作系统——评测一次太慢）

## 关键发现

从 meomory 实践中获得的洞察：

1. **切分是关键** — 把大问题切成可独立进化的小模块，每个模块有自己的评测函数
2. **评测函数比进化策略更重要** — V2 换了评测目标直接超 V1 终点
3. **搜索空间决定天花板** — 单函数卡 38%，扩到类立刻 87.6%
4. **进化能突破人类偏见** — AI 没有"之前试过不行"的包袱
5. **多模型混合比单模型强** — 不同模型贡献不同风格的代码变异

## 愿景

> 最终让所有代码自然生长。
> 人类不再是程序员，而是园丁——定义土壤（评测函数）和阳光（计算资源），代码自己生长出最适合环境的形态。
