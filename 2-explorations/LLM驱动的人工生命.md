# LLM 驱动的人工生命

**日期**：2026年3月31日
**来源**：Ember 改造讨论 → 三管子架构 → ALife 项目调研 → 代码进化 vs 数值进化的本质区别
**状态**：构想阶段，未实现

## 一、核心想法

将 Ember（实时 AI 心跳可视化装置）改造为一个 **LLM 驱动的人工生命生态系统**。不是传统 ALife 的数值进化，而是用 LLM 进化可读的行为代码。每个生物的"基因"是一段人能读懂的代码。

**目标体验**：让观众亲眼看到进化算法的魅力——一群生物在屏幕上竞争、繁殖、死亡，点击任何一个就能透视它的"DNA"（一段可读的代码）。

## 二、为什么是新东西

| | 传统 ALife（Bibites/biosim4） | 纯 LLM 项目（AI-Scientist） | **本项目** |
|---|---|---|---|
| 基因表示 | 浮点数组 | 论文/代码 | **可读的行为代码** |
| 变异方式 | 随机数值扰动 | LLM 改写 | **LLM 改写** |
| 可视化 | 有 | 无 | **有** |
| 可透视基因 | 无（数字看不懂） | 可读但无视觉 | **点击看代码** |
| 进化速度 | 慢（盲搜） | 快 | **快** |
| 涌现复杂结构 | 有限（API太高级） | 不适用 | **未验证** |

**交叉点**：LLM 的代码理解能力 + ALife 的可视化生态 + 低原语设计。据调研，这个组合没有现有项目。

## 四、关键设计原则

### 1. 限制即引擎

不给高级 API。只给最低级的网格读写权限，逼进化自己发明感知、运动、繁殖。

```
每个细胞拥有的全部能力：
- 输入：周围 N 格的原始数值
- 输出：写入自己和相邻格的数值
- 约束：写入消耗能量，能量归零即死
```

没有 sense()，没有 move()，没有 reproduce()。这些都从读写操作中涌现。

### 2. 代码即基因

每个细胞运行一段极简 JS 函数：

```js
// 进化前（第 1 代）
function cell(nearby, energy, mem) {
    return { write: [{dx:1, dy:0, val: energy}], mem }
}

// 进化后（第 N 代）——LLM 变异产物
function cell(nearby, energy, mem) {
    let foodDir = nearby.find(n => n.val > 0.8)
    if (foodDir && energy > 0.5) {
        // 朝食物方向写入自身代码副本 = "移动"
        return { write: [{...foodDir, val: energy-0.1, code: SELF}], mem }
    }
    if (energy > 2.0) {
        // 向空位写入自身代码 = "繁殖"
        let empty = nearby.find(n => n.val === 0)
        if (empty) return { write: [{...empty, code: SELF}], mem: {...mem, children: (mem.children||0)+1} }
    }
    return { write: [], mem }
}
```

### 3. 外观也是基因

可选：每个生物的基因包含行为代码（JS）+ 渲染代码（GLSL）。外观有选择压力时（其他生物能"看到"颜色），视觉进化自然发生——保护色、警告色、性选择。

### 4. 生态而非单体

不是进化一个最优解，而是多个策略共存竞争。会产生军备竞赛：
- 出现"抢食者" → 被迫进化"躲避者"
- 出现"躲避者" → 被迫进化"追踪者"
- 永远不收敛，因为对手也在变

## 六、LLM 变异 vs 传统变异

为什么 LLM 变异能打破传统 ALife 的天花板：

```
传统 GA 变异：[0.32, -0.71, 0.05] → [0.35, -0.71, 0.02]
  = 盲目扰动，不理解含义

LLM 变异：
  输入："这个生物总是饿死，它的代码里没有寻找食物的逻辑"
  输出：添加 foodDir 感知 + 朝食物方向移动的代码
  = 有意识的、基于理解的改进
```

代价：每次变异需要一次 API 调用。但进化效率提升可能是几个数量级——100 代达到传统 10 万代的效果。

## 七、LLM 的语言选择

| 语言 | LLM 训练数据 | 底层程度 | 适合度 |
|------|------------|---------|-------|
| Python/JS（完整） | 极多 | 太高 | ❌ |
| GLSL | 多 | 逐cell并行 | ✅ 渲染层 |
| **极简 JS 函数** | 极多 | 可控 | ✅ 行为层 |
| 自定义 DSL | 零 | 随意 | ❌ LLM 不认识 |

原则：**选 LLM 最熟悉的、最底层的语言**。LLM 的搜索空间 = 训练数据。选不熟悉的语言等于让 LLM 盲搜。

## 八、开放问题

1. **LLM 变异的成本控制** — 100 个生物 × 每代变异 = 大量 API 调用，如何控制？
   - 可能方案：只对 top-K 个体做 LLM 变异，其余用传统交叉/突变
2. **安全沙箱** — 用户浏览器里执行进化出的任意 JS 代码，如何隔离？
3. **代码膨胀** — LLM 倾向写更长的代码，几百代后基因会膨胀到不可读
4. **涌现天花板** — LLM 进化能否真的超越传统 ALife？需要实验验证
5. **观众交互设计** — 如何让非技术观众也能理解"这段代码是眼睛"
6. **fitness 定义** — 纯生存？还是加入观众评分（交互式进化）？

## 九、最小验证实验

如果要做，最小可行版本：

```
- 64×64 网格
- 每个格子：空 或 一段 10 行以内的 JS 函数
- 物理：能量守恒 + 相邻读写
- 变异：每代选 top-10 个体，LLM 变异
- 渲染：Canvas 2D（不需要 WebGL）
- 指标：存活代数、种群多样性、代码复杂度
```

预计能在 1-2 天内验证"LLM 能否在低原语环境下进化出有意义的行为"。
